# vibe-audit — аудит безопасности вайбкод-проекта

Детерминированный сканер + live-проверка своего сайта + чек-лист + твоя голова
поверх. Находит типовые дыры вайбкода и выдаёт отчёт «проблема → фикс» с одной
главной цифрой.

## 0. Принципы (обязательно, нарушение = отказ от задачи)

1. **Только чтение и только свои ресурсы.** Ничего не менять в проекте. Сканер
   пишет только свой отчёт. Live-проверку запускать **ТОЛЬКО** против домена,
   которым владеет пользователь — скрипт сам спросит подтверждение.
2. **Секреты не цитировать.** Скрипты маскируют находки (`sk-pro…op`); ты тоже
   никогда не выводишь значение целиком — даже в чат, даже «просто показать».
3. **Формат «проблема → фикс».** Никогда не объясняй, как эксплуатировать
   находку, не пиши пейлоады, не подсказывай, как сломать. Не сканируй чужие
   домены. Это не входит в задачу и не нужно.
4. **Найден живой ключ → первый пункт ответа «перевыпусти его сейчас».** Не
   «поправь потом». Ключ в git уже скомпрометирован, даже в приватном репо.
5. **Не выдумывай находки.** Если сомневаешься, прочти файл и скажи честно:
   «похоже, но руками не проверил» — это полезнее выдуманной находки.
6. **Ноль находок ≠ безопасно.** Это линтер типовых ошибок, а не пентест.

## 1. Файлы скилла

| Файл | Когда читать |
|---|---|
| `references/checklist.md` | Шаг 4 — что сканер не увидит никогда: лимиты, 2FA, RLS, бэкапы |
| `references/modern-stack.md` | Шаг 3 — что именно v2.0 проверяет в CI/CD, Docker, Terraform, MCP, AI-эндпоинтах |
| `references/report-template.md` | Шаг 5 — структура `vibe-audit-report.md` и правила подсчёта |
| `scripts/audit.py` | Шаг 1 — статический сканер |
| `scripts/livecheck.py` | Шаг 2 — проверка задеплоенного домена (только свой) |
| `tests/run_selftest.py` | Проверка целостности самого скилла (для контрибьюторов) |

Скрипты — **Python 3.9, только стандартная библиотека**. Ничего не ставят, в
проект не пишут.

> **Windows:** `python3` часто указывает на заглушку Microsoft Store, которая
> молча ничего не делает. Проверь `python --version` и используй его. Пути отчётов
> пиши в каталог проекта или в `%TEMP%` — не в `/tmp`.

## 2. Шаг 1 — Статический сканер

```bash
python scripts/audit.py /путь/к/проекту --report vibe-audit-report.md
```

Машиночитаемый вариант (для CI и для разбора):

```bash
python scripts/audit.py /путь/к/проекту --json > audit.json
```

Коды выхода: **0** — только info/чисто · **1** — есть warning · **2** — есть
critical. Ошибка самого сканера тоже даёт ненулевой код и попадает в отчёт как
`check_error` — это баг инструмента, а не находка.

Что ловит (подробно — `references/modern-stack.md`): секреты 30+ провайдеров в
коде, `.env`/`.npmrc`/`*.pem`/`Dockerfile`/`*.tfvars` в репозитории, ключи в
клиентском бандле и публичных env-префиксах, отключённая проверка TLS, CORS `*`,
`debug=True`, `eval`, SQL/командная/NoSQL/SSTI-инъекции, zip-slip, SSRF,
GitHub Actions (`pull_request_target`, секреты в логах), Docker
(`privileged: true`, `curl | bash`, `:latest`, секреты в `ARG`), MCP-конфиг с
секретами, `alg:none`, `Math.random()` в качестве OTP, md5/sha1 для паролей,
отсутствие rate limit, AI-эндпоинты без авторизации и без `max_tokens`, роль из
клиента, IDOR-подозрения, открытые Firebase-правила, дефолтные пароли и проброшенные
порты БД, уязвимые npm-зависимости.

**Скрипт — эвристика по коду, не истина.** Дальше — обязательный ручной проход.

---

## 3. Шаг 2 — Live-проверка своего домена (опционально)

Только если у пользователя есть задеплоенный сайт **и это его домен**:

```bash
python scripts/livecheck.py https://его-сайт.com
python scripts/livecheck.py https://его-сайт.com --json     # для CI
```

Проверяет security-заголовки (CSP, HSTS, X-Frame-Options, nosniff,
Referrer-Policy, Permissions-Policy), флаги кук (`Secure`, `HttpOnly`,
`SameSite`), раскрытие стека и не отдаётся ли наружу то, чего там быть не должно:
`.env`, `.git/config`, дампы, Spring actuator, Swagger/OpenAPI, `.svn`.

Это обычные GET-запросы к своему сайту — тот же класс действий, что
securityheaders.com. Не сканирование уязвимостей и не атака.

**Скрипт требует подтверждения владения** — не обходи это за пользователя без
явного «да, это мой домен» (или флага `--yes-i-own-this`, который ставит только
сам пользователь). В неинтерактивном окружении скрипт завершится с понятным
сообщением, а не с ошибкой — тогда попроси пользователя подтвердить в чате и
запусти с флагом.

## 4. Шаг 3 — Ручной проход (то, что regex не умеет)

Прочитай код и добавь своими секциями то, что сканер пропустить обязан:

- эндпоинты без авторизации — **все** write/delete-роуты, а не только те, где
  сработала эвристика;
- проверка владения ресурсом: пользователь A не должен открыть данные B
  (проверяется с двух аккаунтов руками, не чтением кода);
- валидация пользовательского ввода на сервере;
- бизнес-логика авторизации: может ли пользователь достать чужой файл по
  предсказуемому пути, обойти лимит через другой роут, вызвать дорогую операцию;
- секреты в логах, в аналитике, в error-трекере;
- что происходит при сбое: стектрейс наружу или нет.

**Если хост умеет субагентов** — шаг 3 и разбор отчёта можно раздать параллельно:
один — секреты и инфраструктура, второй — авторизация и инъекции, третий —
CI/CD и зависимости. Каждый отдаёт блок «проблема → фикс» в одном формате,
сводишь ты. Без субагентов — делай сам, последовательно.

---

## 5. Шаг 4 — Чек-лист перед деплоем

Покажи пользователю `references/checklist.md` и пройдитесь по нему вместе: лимиты
расходов в консолях AI, 2FA, RLS, бэкапы (восстановленные, а не «настроенные»),
права сервис-аккаунтов. Это то, что сканер увидеть не может.

---

## 6. Шаг 5 — Отдай результат

- Главная цифра: «N находок: X критичных / Y важных / Z на проверку».
- Оба отчёта (пути) + **топ-3 «чини прямо сейчас»**, отсортированные по ущербу, а не
  по порядку обнаружения.
- Предложи починить по списку — но **не чини сам без просьбы**.
- Не пересказывай весь отчёт в чат: отчёт уже в файле.

Формат отчёта и правила подсчёта — `references/report-template.md`.

---

## 7. Найден живой ключ — порядок действий

1. **Перевыпустить ключ прямо сейчас** в консоли сервиса. Если он был в git —
   он уже скомпрометирован, даже в приватном репо.
2. Убрать из кода, положить в окружение/секрет-менеджер, `.env` — в `.gitignore`.
3. Историю чистит `git filter-repo`, но пункт 1 обязателен в любом случае: чистка
   истории не отзывает уже утёкший ключ.

---

## 8. Ограничения — говори о них честно

Это линтер типовых ошибок + внешняя проверка заголовков, **а не пентест**. Он не
проверяет глубоко логику авторизации, инфраструктуру, права в облачных консолях,
RLS-политики Supabase изнутри, мобильные приложения и бинарники. Чистый отчёт ≠
безопасное приложение. Для продакшена с деньгами и персональными данными нужен
живой специалист.

Пропущенный сканером файл или недоступная проверка **должны быть сказаны вслух**:
«N файлов пропущено как слишком большие», «npm audit не запустился — нет сети».
Пропущенная проверка — это не «зелёная галочка».
